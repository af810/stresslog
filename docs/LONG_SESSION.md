# 長時間計測・時系列グラフ・CSV — v0.6.0

2026-11-17。`feature/long-session`。v0.5.5のUIを通常の計測アプリへ統合し、長時間モードを追加。
推定モデル・特徴量・0–100の意味は変更していない。

## 普段の使い方

1. PCで `Start-StressLog.cmd` をダブルクリックする。
2. 時計を装着し、StressLogの「長時間計測を開始」を押す。
3. PCの `http://localhost:5173/?tab=live` で現在値と時系列グラフを見る。
4. 終わったら時計で「計測を終了」。PC受信機は必要に応じて `scripts/Stop.ps1` で終了。

初回のPC登録が済めば、日常の計測にワイヤレスデバッグ、ADB接続、ポート入力は不要。
ワイヤレスデバッグをオフにしても、アプリ自身のWi-Fi送信は利用できる。アプリの更新・設定変更でADBが必要なときだけオンにする。
時計とPCは同じWi-Fiを使用する。PCの電源・受信機をオンにし、スリープさせないこと。
通常のブラウザを閉じても、PC受信機が動いていれば計算と保存は続く。
WindowsにログインしただけでPC受信機を自動起動する設定は、今回追加していない。

## 時計のモードと電池

- 連続モード: 時間による終了はせず、終了操作か低電池で止まる。
- 7分モード: 従来どおり短時間で終了する。画面上のカウントは5秒間隔の更新。
- 停止残量: 初期値20％。計測画面の下で10 / 20 / 30％を選択でき、次の計測から適用。
- 電池残量が停止値以下の場合は開始しない。計測中にその値へ達するとセンサーと通信を停止。
- 「起動時に自動開始」をオンにすると、接続設定済みの時計アプリをランチャーから開いたとき、長時間計測へ進む。初期値はオフ。
- 手動停止・電池による停止の後は自動開始を抑止し、開始ボタンで再開する。画面に戻っただけで意図せず再開しない。
- 時計の電源投入時、時計アプリの強制終了後、OSによる停止後まで無条件に計測を復帰させる仕組みではない。
- 開始時の権限確認を含むため、初回は画面上の操作が必要。

画面を文字盤へ戻してもフォアグラウンドサービスで取得を続ける。
常時PPGとWi-Fiを使うので、一日中持つ保証はない。今回の改修は、電池を使い切る前の停止と再接続の改善であり、電池持ちの実証ではない。
取り外したときはPCで非装着の区間を推定対象から外す。センサーの自動停止・再開は行わない。

## ずっと見られる記録

- 現在値: 従来どおり約60秒窓で推定。
- 時系列: おおむね15秒以上の間隔で、有効な推定だけを時刻付き保存。連続する60秒窓は重複しており、独立した試験ではない。
- 表示: 直近1時間 / 6時間 / 1日、過去の日付を選択可能。日付一覧は最近30ファイル分。
- 45秒を超える保存間隔やセッション変更でグラフの線を切り、欠測を補間して連続した測定と見せない。
- 保存先: `.stresslog-local/live/population/daily/YYYY-MM-DD.jsonl` と同名の `.csv`。
- CSVは受信中に自動追記する。ブラウザの「この日のCSVを保存」でも取得可能。
- CSV列: `time_jst,score,prv_used,outside_training_range`。時刻は日本時間のISO形式、scoreは丸める前のモデル出力。
- JSONLを復元元とし、PC受信機を再起動して新たに計測したときCSVを再構築してから追記する。
- 日ごとに最大7,000件・読み込み6 MBを上限としてメモリと処理を制限。保存失敗や壊れたファイルは画面にエラーを出し、黙って上書きしない。
- 日別ファイルを自動削除する処理はない。長期利用時は空き容量を確認する。
- 生PPG・生加速度を長期間すべて保存する機能ではない。既存の任意キャプチャ機能とは別。

通信断の間はPCへ届かず、記録できない。時計は最新の数十秒程度のイベントと送信待ちバッチに制限し、メモリを増やし続けない。
長時間オフラインの全波形を時計内へ保存し、後からすべて復元する機能は実装していない。
記録は「受信・品質条件を通過した区間の推定スコア」であり、本人のストレスの上限や、欠測区間の心理状態を示さない。

## 自動接続の仕組み

初回設定で渡した証明書とトークンを引き続き使用。
受信先が同じなら、そのHTTPS接続を再試行する。失敗が続くと、同じWi-Fi内でPCを探索する。

- 接続再試行: 6秒から最大60秒まで待ち時間を延長。
- PC探索: UDP 8789、最大約1分に1回。常時探索しない。
- 時計は乱数nonceと接続キーによるHMACを送り、PCの応答もnonce・ポートを含むHMACで照合。
- トークンそのもの、個人の計測値、証明書は探索パケットに載せない。
- 見つかったアドレスでも、**初回設定と完全に一致するTLS証明書**だけを受け付ける。証明書の有効期限も検査する。
- DHCPでPCのIPが変わっても、証明書とキーが同じなら再発行・再ペアリングを避けられる。
- ルーターの端末間通信制限やブロードキャスト制限で探索できない場合は、保存済みアドレスへの再接続を続ける。
- ファイアウォールはプライベートLAN内のTCP 8787とUDP 8789が必要。PC内部API 8788とWeb 5173は外へ開放しない。
- 証明書期限切れ、キーの変更、別PCへの移行時は初回設定のやり直しが必要。

更新などでADBが必要な場合も、`scripts/Configure-Watch.ps1` は単一の接続済み端末またはmDNS広告を探すので、通常は `-DeviceAddress` を省略できる。
ペアリング自体が切れている場合は時計に表示されたコードが必要で、無断で迂回しない。

## フリーズ対策の範囲

以前のv0.5.3/4で見られたフリーズの根本原因は確定していない。
今回は非装着時の停止・再開、AlarmManagerによる再起動、ライフサイクルロックを保持したスレッド間の待ち合わせを削除。
センサー登録・解除をセンサー用スレッドへ寄せ、画面スレッドでそれらの完了を待たない。
これにより疑わしい構造を取り除いたが、長期の安定性を保証する検証には実機で時間が必要。
確認済みv0.5.2 APKは変更せず、必要に応じた復帰用として保持する。

## 更新用APK

`releases/watch/stresslog-watch-v0.6.0.apk` と `long-session.json`（SHA-256）を同梱。
PC受信機を起動し、ペアリング済みの時計でワイヤレスデバッグをオンにしてから:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Install-LongSession.ps1
```

単一の時計なら接続先を自動検出する。複数端末がある場合は `-DeviceAddress IP:PORT` で指定。
通常の開始時にはAPKの再インストールもADB接続も不要。
元PCではv0.5.2とv0.6.0の署名が一致することを確認し、`install -r`でデータを保持して更新した。
別署名・別の新しいバージョンが既に入っている場合、勝手に削除して入れ直さない。

## 検証

Webテスト109件、PC受信機29件、時計の電池停止境界・再接続間隔の単体テスト2件を実行。
Webビルド、時計通常版・UIプレビュー版ビルド、Android lintでエラー0件。
Windows日本語パス上のGradleのテストワーカー起動が失敗したため、同じコンパイル済み時計テストはJDKのJUnitCoreで実行して2件通過を確認。
実機での受信・長時間計測・再接続・低電池停止の確認状態は `docs/LONG_SESSION_VALIDATION.json` に記録する。

実機確認中に見つかった問題も修正した。

- 電池の初期通知がコールバックより先に取得可能なため、返されたsticky Intentから直ちに残量を読むよう修正。通知到着待ちを電池不明と誤認しない。
- PC受信機再起動時に装着状態を失わないよう、最後に観測した装着状態とその元のセンサー時刻を各バッチへ付加する。過去のイベントを新しい測定時刻に作り替えない。
- 受信機は装着状態の時刻を照合し、古い値で新しい状態を上書きしない。再接続に関する回帰テストを追加。
